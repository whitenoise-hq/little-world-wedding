# 기획: 리틀 월드 웨딩

게임처럼 캐릭터를 움직이며 둘러보는 픽셀아트 모바일 청첩장이다. 화면 구조와 기능은 하나로 두고, 무대(테마)만 골라 쓴다. 커플마다 데이터를 넣어 각자 고유한 주소를 준다.

- 참고한 청첩장: https://our-little-wedding.vercel.app/village/ (코드나 그림은 가져다 쓰지 않고 구조만 참고)
- 목업: [우주 테마](mockup/index.html), [마을 테마](mockup/village.html). 브라우저로 열면 바로 움직여 볼 수 있다. 화면 왼쪽 위 버튼으로 테마를 오간다.
- 목업은 방향을 잡기 위한 시안이다. 세부는 구현하면서 조정하고, 바뀐 결정은 이 문서에 먼저 반영한다.

## 1. 서비스 구조

```
{도메인}/{slug}      → 커플별 청첩장 (apps/web)
admin.{도메인}       → 어드민. 청첩장 생성·수정, 운영자 1명만 사용 (apps/admin)
```

| 항목 | 결정 |
|---|---|
| 레포 구조 | Turborepo + pnpm 모노레포. 하객용 화면과 어드민을 별도 앱으로 나눔 |
| 프레임워크 | 두 앱 모두 Next.js (App Router). 하객용은 `/[slug]` 동적 라우트 하나로 모든 청첩장 처리 |
| DB·저장소 | Supabase (DB, 사진 스토리지, 어드민 로그인) |
| 게임 화면 | 2D 캔버스 픽셀아트. 무거운 엔진(three.js 등) 없이 가볍게 |
| 어드민 | 운영자만 관리. 신랑·신부 로그인 없음 |
| 배포 | Vercel 프로젝트 2개 (web, admin). 바뀐 앱만 빌드 (`turbo-ignore`). 함수 실행 위치는 서울(`icn1`)로 고정해 서울 리전 Supabase와 가깝게 둔다 |

### 모노레포 구성

```
apps/
  web/        하객용 청첩장 (/[slug], 인트로, 게임 화면, 모달, 방명록 쓰기)
  admin/      어드민 (청첩장 입력, 사진 업로드, 방명록 관리, 테마 미리보기)
packages/
  engine/     캔버스 게임 엔진 + 테마(space, village). web과 admin 미리보기가 같이 씀
  shared/     도메인 타입, zod 스키마, slug 생성, Supabase 타입, 공통 상수
```

- **나누는 이유:** 하객용 화면에 어드민 코드가 섞이면 안 되기 때문이다. Next.js는 라우트별로 코드를 나누므로 한 앱이어도 하객이 받는 JS가 커지지는 않는다. 그래도 나누면 다음이 좋다.
  - 어드민 전용 의존성(폼, 이미지 업로드, UI 라이브러리)과 서버 권한 키가 하객용 배포에 아예 들어가지 않는다.
  - 어드민을 고쳐도 하객용 청첩장이 다시 배포되지 않는다. 결혼식 직전에 하객 화면이 흔들릴 일이 줄어든다.
  - 도메인과 인증을 따로 둘 수 있다(어드민은 `admin.` 서브도메인 + 로그인).
- **공유 규칙:** 두 앱이 같이 쓰는 것(타입, 스키마, 상수, 엔진·테마)은 `packages/`에만 둔다. 앱끼리 서로 import하지 않는다.
- **테마 미리보기:** 어드민에서 입력한 데이터로 청첩장을 미리 볼 때 `packages/engine`을 그대로 쓴다. 하객 화면과 미리보기가 어긋나지 않게 하려는 것이다.

### slug 규칙

- 영어 소문자 8자리 무작위 문자열 (예: `/ejdushfe`). 경우의 수 약 2,090억(26⁸)이라 추측해서 찾기 어렵다.
- 대소문자를 섞지 않는다. 카톡·문자로 전달하거나 손으로 칠 때 헷갈리지 않게 하려는 것이다.
- `crypto.getRandomValues`로 생성한다. `Math.random`은 쓰지 않는다.
- 256은 26으로 나누어떨어지지 않으므로, 234 이상인 바이트는 버리고 다시 뽑는다(모든 글자가 같은 확률로 나오게).
- DB에 unique 제약을 걸고, 겹치면 다시 생성한다.
- 홍보용 샘플 청첩장만 예외로 기억하기 쉬운 주소를 쓴다(`/seavilla`, `/marsland`, 7장 "샘플(템플릿) 청첩장").
- 어드민에 "주소 다시 만들기" 버튼을 둔다. 링크가 원치 않는 곳에 퍼졌을 때 쓴다.
- 검색에 노출되지 않게 `noindex`를 건다.
- 없는 주소, 비공개 청첩장, 루트(`/`)로 들어오면 "청첩장을 찾을 수 없습니다" 안내 페이지를 보여준다. 보낸 분께 주소를 다시 확인해 달라고 안내하고, 아래에 샘플 청첩장(마을·우주) 링크를 둔다.

```ts
const ALPHABET = 'abcdefghijklmnopqrstuvwxyz'
const SLUG_LENGTH = 8
const LIMIT = 256 - (256 % ALPHABET.length) // 234

export function generateSlug(): string {
  let slug = ''
  while (slug.length < SLUG_LENGTH) {
    for (const b of crypto.getRandomValues(new Uint8Array(SLUG_LENGTH))) {
      if (b < LIMIT && slug.length < SLUG_LENGTH) slug += ALPHABET[b % ALPHABET.length]
    }
  }
  return slug
}
```

## 2. 테마

모든 테마는 같은 규칙을 따른다. 장소 3곳(집·사진·방명록), 같은 모달 내용, 같은 조작, 같은 캐릭터를 쓰고 그림과 방명록 연출만 다르다. 어드민에서 청첩장마다 테마를 하나 고른다.

### 공통 그림 규칙

- **화면 배율:** 저해상도(114×227)로 그린 뒤 3배 확대해 픽셀을 또렷하게 보여준다. 월드(200×340)가 화면보다 크고, 카메라가 캐릭터를 따라 상하좌우로 움직인다.
- **그림 스타일:** 색 수를 제한한 팔레트, 디더링 음영, 모든 물체에 어두운 외곽선(`#2a1a2e`). 픽셀 폰트는 갈무리(Galmuri11).
- **겹침 순서:** 물체를 발밑 y좌표 순으로 그려서 캐릭터가 물체 앞뒤로 자연스럽게 지나간다.
- **방명록 오브젝트:** 글 하나가 오브젝트(별·물고기) 하나다. 위치·색·움직임은 글 id의 해시로 정해서 다시 들어와도 같다. 누르면 그 글(이름·메시지)이 **화면 위쪽 가운데에 고정된 카드**로 뜨고, 누른 오브젝트 위에 하트가 깜빡인다. 몇 초 뒤 또는 다른 곳을 누르면 사라진다.

### 테마 비교

| | 우주 (`space`) | 마을 (`village`) |
|---|---|---|
| 무대 | 마션풍 붉은 행성(원형). 아래로 우주가 펼쳐짐 | 숲으로 둘러싸인 마을. 아래로 해변과 바다 |
| 이동 범위 | 행성 가장자리 안쪽 | 숲 안쪽 육지 + 부두 (바다는 부두로만 들어감) |
| 집 | 컨테이너형 거주 모듈 (태양광 패널, 안테나, 둥근 창, 착륙 다리) | 빨간 지붕 집 (굴뚝 연기, 하트 장식 문, 창가 화분, 우체통) |
| 사진 | 투명 돔 온실 (해바라기, 토마토 덩굴, 꽃 화단) | 분홍 줄무늬 정자 (안에 사진이 걸려 있음, 옆에 삼각대 카메라) |
| 방명록 | 땅 끝 전망대의 망원경 | 바다로 뻗은 부두 끝 낚시터 (낚싯대, 찌, 양동이) |
| 방명록 오브젝트 | 우주에 뜬 **별** | 바다에서 헤엄치는 **물고기** (6가지 색) |
| 글을 남기면 | 별똥별이 날아가 새 별로 자리 잡음 | 찌 자리에서 물고기가 첨벙 뛰어올라 바다로 들어감 |
| 오브젝트 보이는 조건 | 항상 보임 | 멀리서는 그림자, 해변·부두에 가까이 가면 색이 보임 |
| 시작 위치 | 행성 가운데 | 웨딩 입구 바로 앞. 처음 들어오면 신랑·신부 바로 뒤에 입구가 보임 |
| 고정 장식 | 탐사 로버, 위성 안테나, 하트 깃발, 크리스탈, 빛나는 외계 식물, 연못, 크레이터 | 웨딩 입구(하트 장식 꽃 아치, 흰 천), 입구부터 이어진 흰 버진로드, 버진로드 끝의 작은 분수, 나무, 꽃밭, 가로등, 표지판, 나룻배, 등대 |
| 움직이는 장식 | 줄전구, UFO, 별똥별, 반짝이는 별, 안테나 불빛 | 줄전구, 분수 물줄기, 분수 주위를 뛰어다니다 가끔 앉는 흰 강아지, 해변을 오가는 거북이, 굴뚝 연기, 나비, 갈매기, 파도 거품, 물결 반짝임, 등대 불빛, 카메라 플래시 |
| 모달 헤더 색 | `#2a2450` (밤하늘 남색) | `#1e4660` (바다 남색) |

새 테마를 추가할 때는 위 표의 칸을 모두 채우고, 이동 범위와 자동 이동 경로(6장)를 함께 정한다.

## 3. 첫 화면 (인트로)

접속하면 게임 화면 위에 전체화면 인트로를 먼저 띄우고, 그 뒤에서 게임을 불러온다. 로딩 화면을 기다림이 아니라 청첩장 표지처럼 쓰는 것이 목적이다.

- **내용:** 신랑·신부 이름(`원재 ♥ 은빈`)과 날짜·시간만 둔다. 따로 문구는 넣지 않는다. 테마 색 배경에 글자는 나눔명조로 차분하게 쓴다. 게임 캐릭터 둘이 제자리에서 걷는 작은 그림만 픽셀로 둔다(앞으로 들어갈 게임 세계의 예고).
- **로딩 표시:** 문구 아래에 얇은 진행 막대를 둔다. 기준은 게임 코드, 폰트, 첫 화면 그림 준비다. 사진은 기다리지 않는다.
- **들어가기:** 준비가 끝나면 진행 막대가 "들어가기" 버튼으로 바뀐다. 누르면 인트로가 부드럽게 걷히며 게임 화면이 나온다.
  - 자동으로 넘기지 않고 한 번 누르게 한다. 표지를 읽을 시간을 주고, 이 터치로 브라우저의 소리 재생 제한이 풀려서 배경음악을 켤 수 있게 된다.
  - 빨리 불러왔으면 버튼이 바로 보인다. 일부러 기다리게 하지 않는다.
- **서버에서 바로 그린다:** 인트로는 `/[slug]`에서 서버가 HTML로 바로 보내는 화면이다. 게임 코드·사진과 관계없이 첫 화면이 즉시 뜬다. 폰트가 늦으면 시스템 폰트로 먼저 보여준다.
- **청첩장 바로 보기:** "들어가기" 아래에 같은 크기·모양의 버튼을 하나 더 둔다(반투명 바탕에 흰 글자). 게임 조작이 어려운 분(어르신 등)을 위한 길이다.
  - 게임 코드를 기다릴 필요가 없으므로 진행 막대가 차는 동안에도 처음부터 보이고 누를 수 있다.
  - 누르면 **전체화면 모달**이 열린다. 머리에는 왼쪽 위 닫기(✕) 버튼만 둔다. 닫으면 다시 표지로 돌아온다.
  - 내용은 위에서 아래로: 이름·날짜 → 청첩장 모달 내용 전체(인사말, 일시, 오시는 길, 연락처, 계좌) → 사진(사진이 있을 때만) → 방명록. 장소 모달과 같은 화면 구성을 그대로 쓴다.
  - 여기서 방명록을 남기면 연출 없이 목록에 바로 더하고 "축하 메시지를 남겼습니다" 토스트만 띄운다. 게임 화면에는 오브젝트가 더해져 있어서 나중에 들어가도 보인다.
- **다시 방문:** 같은 기기에서 다시 들어오면(로컬 저장) 인트로를 짧게 보여주거나 바로 버튼 상태로 시작한다.
- "조이스틱이나 버튼으로 움직여 보세요" 안내는 인트로를 지나 게임 화면에 처음 들어왔을 때 띄운다.

## 4. 장소와 모달

| 장소 (세계 안 이름) | 플로팅 버튼 | 들어가기 버튼 | 모달 제목 | 모달 내용 |
|---|---|---|---|---|
| 집 | 청첩장 | 청첩장 보기 | 청첩장 | 인사말, 일시, 장소, 오시는 길, 연락처, 계좌 (한 모달에 스크롤) |
| 정원 / 온실 | 사진 | {장소} 들어가기 | 사진 | 사진 갤러리 |
| 낚시터 / 망원경 | 방명록 | {장소} 들어가기 | 방명록 | 방명록 쓰기·목록 |

- 플로팅 버튼과 모달 제목은 하객이 무엇을 볼 수 있는지 바로 알도록 용도로 쓴다(청첩장·사진·방명록). 세계 안의 집은 "집"이라고 하면 예식 정보가 있는 곳인지 알기 어렵기 때문이다.
- 장소 가까이 가면 들어가기 버튼이 뜬다. 집은 "청첩장 보기", 나머지는 "{장소} 들어가기"(예: 정원 들어가기, 낚시터 들어가기)로 테마의 재미를 살린다.
- "우리 집"이라는 이름은 쓰지 않는다.

### 집 모달 (위에서 아래로)

1. **인사말:** 소개 문구(인사말)만 둔다. "○○ · ○○의 아들/딸" 같은 부모님 소개 줄은 넣지 않는다(부모님 성함은 연락처에만 쓴다)
2. **예식 일시:** 날짜·요일·시간, 달력(해당 날짜 표시), D-day
3. **예식 장소:** 예식장 이름·홀, 주소(복사 버튼), 카카오맵, 길찾기 버튼(카카오맵, 네이버지도, 티맵)
4. **오시는 길:** 지하철, 버스, 주차, 기타 안내 (어드민에서 항목 추가)
5. **연락처:** 위에 신랑(왼쪽)·신부(오른쪽) 두 칸. 그 아래 "신랑 측 혼주 ⌄ 신부 측 혼주" 줄 전체가 접기·펼치기 버튼이다. 처음에는 펼쳐져 있어 각 열 아래에 아버지·어머니 카드가 보이고, 누르면 부드럽게 접히고 펴진다. 카드마다 이름과 전화·문자(편지봉투) 아이콘 버튼(글자 없음). 부모님은 어드민에서 번호를 공개한 분만 보인다.
6. **마음 전하실 곳:** 신랑 측 / 신부 측 아코디언. 사람마다 은행, 계좌번호, 예금주, 복사 버튼. 카카오페이 송금 버튼은 선택.

### 모달 디자인

- 화면 가운데에 떠 있는 패널로, 사방 5%씩 띄워 **화면의 90%** 를 채운다.
- **모달 안은 진지한 청첩장 디자인이다.** 픽셀 느낌을 쓰지 않는다(픽셀은 게임 캔버스에만). 규격은 `docs/ART_GUIDE.md` 6장.
  - 따뜻한 흰 바탕, 모서리 16px, 옅은 그림자. 열 때 살짝 떠오르며 페이드인.
  - 헤더는 제목과 닫기(✕) 아이콘만 두고 바탕과 같은 색으로 담백하게.
  - 섹션 제목은 영문 라벨 + 한국어 제목(INVITATION / 초대합니다).
- 본문만 스크롤한다. 스크롤바는 얇고 옅은 회색.
- 닫기 버튼이나 바깥 어두운 영역을 누르면 닫힌다.

### 사진 모달

- 모든 사진을 **가로 3칸 격자**로 쭉 나열한다. 정사각형 썸네일에 번호를 작게 표시한다.
- 썸네일을 누르면 **전체화면 보기**가 뜬다. **사진만** 보여준다(번호·설명 글자 없음). 닫기(✕) 아이콘만 둔다.
- 좌우로 밀어서 넘긴다. 손가락을 따라 자연스럽게 밀리는 기본 슬라이드로, 라이브러리 없이 CSS scroll-snap으로 만든다. 처음과 끝에서 멈춘다.
- PC(마우스)에서는 양옆에 이전·다음 화살표를 보여주고, 방향키·Esc도 받는다.
- 큰 사진은 지금 사진과 양옆 사진만 불러온다.
- 어드민 사진 항목의 한 줄 설명(선택)은 화면에 보이지 않고 대체 텍스트(alt)로 쓴다.

## 5. 방명록

- 입력: **이름, 메시지** 두 가지만 받는다. 비밀번호는 받지 않는다.
- 입력 폼 위에 글이 무엇이 되는지 한 줄로 알린다. 마을: "남겨 주신 메시지는 바다의 물고기 한 마리가 됩니다." / 우주: "남겨 주신 메시지는 하늘의 별 하나가 됩니다."
- **한 번 남긴 글은 작성자가 수정하거나 지울 수 없다.** 입력 폼 아래에 "남긴 글은 수정하거나 지울 수 없어요"라고 알린다.
- 글을 남기면 모달이 닫히고, 카메라가 방명록 영역으로 잠시 이동해 새 오브젝트가 생기는 연출을 보여준다. 새 오브젝트는 한동안 강조 표시(별은 크게, 물고기는 머리 위 하트)를 한다.
- 모달 안에는 전체 글 목록도 같이 보여준다.
- 운영자는 어드민에서 어떤 글이든 삭제할 수 있다. 작성자가 지울 수 없으므로 운영자 삭제가 유일한 정리 수단이다.
- 스팸 방지 대책이 필요하다. 같은 기기·IP의 연속 작성 제한, 글자 수 제한(이름 12자, 메시지 120자)을 기본으로 둔다.

## 6. 캐릭터와 조작

- 나중에 어드민에서 헤어스타일과 옷 색을 고를 수 있게 한다 (둘을 닮게 만드는 것이 핵심).

### 조작

| 요소 | 위치 | 동작 |
|---|---|---|
| 조이스틱 | 왼쪽 아래, 고정형 | 미는 방향과 세기만큼 걷기. 가운데 작은 데드존. 상하좌우에 픽셀 화살표가 있고, 미는 방향의 화살표가 노란색으로 켜진다 |

## 7. 어드민 입력 항목 (청첩장 1건)

| 구분 | 항목 |
|---|---|
| 기본 | slug(자동 생성, 재발급), 공개/비공개 |
| 테마 | 우주 / 마을 중 선택 |
| 인물 | 신랑·신부 이름, 양가 부모님 성함 |
| 인사말 | 인사말 글 |
| 예식 | 날짜·시간, 예식장 이름, 홀, 주소, 좌표, 교통 안내 |
| 연락처 | 신랑, 신부, 양가 부모님 전화번호. 사람마다 노출 여부 |
| 계좌 | 신랑 측·신부 측 계좌 목록. 사람마다 노출 여부, 카카오페이 링크(선택) |
| 사진 | 사진 여러 장(순서 변경, 사진별 한 줄 설명), 카톡 공유용 대표 사진. 아래 "어드민 사진 관리" 참고 |
| 배경음악 | 음악 파일 주소 (선택). 하객 화면에서는 꺼진 상태로 시작 |
| 방명록 | 글 목록, 삭제 (운영자만) |

### 어드민 사진 관리

- 여러 장을 한 번에 고르거나 끌어다 놓아 올린다. 청첩장 하나에 최대 30장.
- **브라우저에서 줄여서 올린다.** 원본은 올리지 않고 두 벌을 만든다: 썸네일(긴 변 600px, 사진 격자용), 큰 사진(긴 변 1920px, 전체화면용). 둘 다 WebP. 사진 방향(EXIF 회전)을 바로잡는다.
  - 저장 경로: `photos/{청첩장 id}/{사진 id}-thumb.webp`, `-full.webp`. 버킷은 공개 읽기, 쓰기는 운영자만(RLS).
  - 아이폰 HEIC는 브라우저가 읽을 수 있을 때만(사파리 등) 올라간다. 안 되면 JPG로 바꿔 올리라고 안내한다.
- 사진마다: 앞·뒤로 순서 바꾸기, 대표 사진(카톡 미리보기) 지정, 한 줄 설명(화면에는 안 보이고 대체 텍스트), 삭제(저장소 파일까지 삭제).
- 대표 사진을 지정하지 않으면 카톡 미리보기에는 첫 번째 사진을 쓴다.

### 샘플(템플릿) 청첩장

홍보용으로 공개해 두는 청첩장이다. 테마마다 하나씩 둔다.

| 테마 | 주소 | 신랑 ♥ 신부 |
|---|---|---|
| 마을 | `/seavilla` | 최신랑 ♥ 박신부 |
| 우주 | `/marsland` | 최신랑 ♥ 박신부 |

- 내용(인사말, 일시, 장소, 연락처, 계좌, 샘플 방명록)은 `packages/shared/src/fixtures.ts` 한 곳에 정의한다. `pnpm db:templates`로 DB에 적용한다.
- 전화번호·계좌는 실제로 연결되지 않는 가짜 값(`010-0000-0000`, `000-...`)만 쓴다. 장소는 가상의 예식장 이름에 공공장소 주소를 쓴다.
- 사진은 어드민에서 직접 올린다(상업 이용 가능한 사진만). 템플릿 적용은 올린 사진을 건드리지 않는다.
- 방명록은 방문자가 직접 써 볼 수 있게 열어 둔다. 연속 작성 제한은 그대로이고, 이상한 글은 어드민에서 지운다. 템플릿을 다시 적용해도 방문자 글은 지우지 않는다(방명록이 비어 있을 때만 샘플 글을 넣는다). 샘플 글 내용을 바꿨을 때는 `pnpm db:templates --reset-samples`로 샘플 글만 갈아 끼운다.

## 8. 데이터·백엔드

- **Supabase 무료 플랜**을 쓴다(DB, 사진 스토리지, 어드민 로그인). 백엔드 서버는 따로 두지 않고 Next.js 서버 코드(Route Handler, Server Action)가 그 역할을 한다.
- 프로젝트: `little-world-wedding`, 리전 Northeast Asia (Seoul). Data API 켬, 새 테이블 자동 공개 끔(권한은 마이그레이션에서 직접 부여), 자동 RLS 켬.

### 접근 방식 (확정)

- **하객 브라우저는 Supabase에 직접 붙지 않는다.** `apps/web`의 서버 코드만 DB를 부른다(slug로 청첩장 하나 읽기, 사진 목록, 방명록 읽기·쓰기). 브라우저에는 Supabase 키가 없다. 공개 키로 청첩장 목록을 긁어 가는 일을 원천 차단한다.
- `apps/web` 서버는 자기 전용 secret 키를 쓴다(서버 환경변수에만). `apps/admin`은 별도 secret 키를 쓴다. 한쪽 키가 새면 그 키만 폐기한다.
- **어드민은 Supabase Auth 로그인 + RLS.** 운영자 계정은 대시보드에서 직접 만들고 회원가입은 끈다. RLS는 운영자 목록(`admins` 테이블)에 있는 사용자만 모든 작업을 허용한다.
- 테이블에는 익명(anon) 정책을 두지 않는다. 키가 새도 막히는 이중 안전장치다.
- 마이그레이션은 레포 루트 `supabase/`에서 Supabase CLI로 관리하고, DB 타입은 `packages/shared`로 생성한다.

### 매일 깨우기 (필수)

Supabase 무료 플랜은 최근 7일 동안 DB 활동이 충분하지 않으면 프로젝트를 일시 정지한다. 기준은 수정이 아니라 **활동**(읽기 포함)이다. 청첩장은 만든 뒤 거의 수정하지 않고, 링크를 돌리기 전이나 결혼식 뒤에는 방문도 뜸하다. 게다가 청첩장 페이지를 캐시하면 하객이 들어와도 DB까지 요청이 가지 않을 수 있다.

- 하루 한 번 `apps/web`의 헬스체크 주소(예: `/api/health`)를 부른다.
- 헬스체크는 **DB에 가벼운 조회를 한 번** 한다. 캐시를 쓰더라도 이 요청은 반드시 DB까지 가게 만든다(캐시 끄기, 동적 응답).
- 스케줄은 Vercel Cron(무료 플랜도 하루 1회 가능) 또는 GitHub Actions 스케줄로 돌린다.
- 헬스체크 주소는 비밀 토큰으로 보호해 아무나 부르지 못하게 한다.
- **구현:** `apps/web`의 `GET /api/health`가 `invitations`를 한 행 조회한다. `apps/web/vercel.json`의 Cron이 매일 03:00 UTC(한국 12:00)에 부른다(무료 플랜은 그 시각 안에서 조금 늦게 돌 수 있다). `CRON_SECRET`이 없거나 틀리면 401.

### 캐시

- 하객 페이지의 **청첩장 내용과 사진 목록은 캐시**한다(Vercel 데이터 캐시, `apps/web/src/lib/cached.ts`). 어드민에서만 바뀌는 데이터라 매번 DB에 묻지 않는다.
- **방명록은 캐시하지 않는다.** 하객이 남긴 글이 바로 보여야 한다. 방명록 조회가 실패해도(예: DB 일시 정지) 빈 목록으로 두고 청첩장은 캐시로 계속 보여준다.
- **갱신:** 어드민에서 저장·공개 전환·주소 재발급·삭제·사진 변경을 하면 하객용 앱의 `POST /api/revalidate`(`REVALIDATE_TOKEN`)를 불러 해당 태그(`invitation:{slug}`, `photos:{청첩장 id}`)를 바로 지운다. 주소를 다시 만들면 예전 주소의 캐시도 지워 예전 링크가 더는 열리지 않게 한다.
- **안전망:** 갱신 호출이 실패해도 1시간이 지나면 저절로 새로 읽는다.
- 헬스체크(매일 깨우기)는 캐시를 거치지 않고 항상 DB까지 간다.

### 데이터 구조 (초안)

1단계 화면을 만들며 다듬는 초안이다. 확정은 Supabase 연결 직전에 한다. 코드상 정의는 `packages/shared`의 zod 스키마(`invitation.ts`)가 기준이다.

| 테이블 | 필드 |
|---|---|
| `invitations` | id, slug(unique), theme, is_published, content(jsonb), cover_photo_id, created_at, updated_at |
| `photos` | id, invitation_id, thumb_url, full_url, caption, sort_order |
| `guestbook_entries` | id, invitation_id, name, message, created_at |

- **content(jsonb):** 청첩장 단위로 한꺼번에 읽고 저장하는 내용은 jsonb 하나에 둔다. 따로 검색할 일이 없고, 항목이 바뀌어도 마이그레이션이 거의 필요 없다.
  - `groom` / `bride`: 이름(성 포함), 이름표용 이름, 전화번호와 노출 여부, 아버지·어머니(이름, 전화번호와 노출 여부)
  - `greeting`: 인사말
  - `ceremony`: 날짜, 시간, 예식장 이름, 홀, 주소, 좌표
  - `directions`: 교통 안내 목록 (항목 이름 + 내용. 지하철·버스·주차 등)
  - `accounts`: 신랑 측·신부 측 계좌 목록 (관계, 예금주, 은행, 계좌번호, 카카오페이 링크, 노출 여부)
  - `decor`: 배경음악 등 꾸미기 (캐릭터 헤어·옷 색은 2단계에서 추가)
- 사진과 방명록은 따로 늘어나고 지워지므로 별도 테이블로 둔다.
- 화면 코드는 저장소 인터페이스(`packages/shared`의 repository 타입)만 쓴다. 1단계 화면 작업 중에는 목업(in-memory) 구현을 쓰고, Supabase 구현으로 바꿔도 화면 코드는 고치지 않는다.

## 9. 꼭 챙길 것

1. **카톡 공유 미리보기:** 청첩장마다 OG 태그(제목, 설명, 대표 사진)를 다르게 생성한다. 가장 중요하다. `/[slug]`의 `generateMetadata`로 처리하므로 1단계에서 함께 만든다.
2. **사진 최적화:** 업로드할 때 리사이즈·압축한다.
3. **배경음악:** 꺼진 상태로 시작한다. 게임 화면 오른쪽 위 픽셀 음악 버튼으로 켜고 끈다. 반복 재생, 앱이 백그라운드로 가면 멈춘다. 어드민에서 음악 주소를 넣지 않으면 버튼도 없다.
4. **저작권:** 그림·폰트·음악은 상업적 이용이 가능한 것만 쓴다. 갈무리 폰트는 OFL이다.
5. **로딩·성능:** 픽셀을 코드로 그리는 비용은 작다. 목업 측정 기준 첫 화면 준비 약 20ms, 프레임당 약 0.5ms(데스크톱)이다. 무거운 것은 외부 파일과 사진이다(목업 기준 아이콘 폰트 865KB, 갈무리 폰트 505KB).
   - **아이콘:** 아이콘 폰트를 쓰지 않는다. 실제로 쓰는 아이콘(약 15개)만 SVG로 넣는다.
   - **폰트:** 갈무리에서 필요한 글자(한글 상용 2,350자, 영문, 숫자, 기호)만 남긴 서브셋을 직접 호스팅한다(목표 150KB 이하). `font-display: swap`을 쓰고 미리 불러온다(`preload`).
   - **사진:** 업로드할 때 격자용 썸네일과 전체화면용 큰 사진을 따로 만든다(WebP/AVIF). 썸네일은 사진 모달을 열 때, 큰 사진은 누를 때 불러온다. 다음·이전 사진은 미리 불러온다.
   - **게임 코드:** 게임 화면은 별도 청크로 나눠 인트로가 떠 있는 동안 불러온다. 배경처럼 움직이지 않는 그림은 처음 한 번만 그려 두고, 매 프레임에는 움직이는 것만 다시 그린다.
   - **배터리:** 모달이나 전체화면 사진이 열려 있거나 앱이 백그라운드로 가면(`visibilitychange`) 그리기 루프를 멈춘다. 30fps로 제한한다.
   - **목표:** 모바일 데이터로 카톡 인앱 브라우저에서 열었을 때 인트로가 1초 안에 뜨고, 3초 안에 들어갈 수 있다. 실제 폰(저사양 안드로이드 포함)에서 측정한다.
